WINDOWS MEMORY FORENSICS — PART 02

DLL analysis, reflective injection, and process hollowing: what's really loaded inside a process

Part 01 covered finding processes Windows doesn't want you to see. Part 02 covers what's actually loaded and running inside a process once you've found it — parsing EPROCESS/PEB/VAD, detecting DLL injection with windows.ldrmodules, and recognizing reflective injection and process hollowing.

Series — Windows Memory Forensics, Part 02 Topic — EPROCESS, PEB, VAD, ldrmodules, Reflective Injection Read — ~16 min

In Part 01 we covered how Windows tracks processes (pslist) and how to find processes that have been hidden or removed from that tracking (psscan). Once a suspicious process has been identified, the next question is usually:

What is actually loaded and running inside that process?

This part covers how to answer that: parsing the core process structures, detecting DLL injection through the Windows loader, understanding reflective (loader-less) injection, and identifying process hollowing — using the windows.ldrmodules plugin as the central tool.

01Parsing process-related structures

After identifying the kernel structures relevant to a process, the next step is to parse the structures that describe what's actually running inside it.

1.1 EPROCESS (Executive Process Block)

Represents every running process. Contains:

  • PID
  • Parent process
  • Threads
  • Access Token
  • Handles
  • PEB
  • VAD
Core process structure in Windows memory.

1.2 PEB (Process Environment Block)

Stores process-specific information:

  • Executable path
  • Command line
  • Environment variables
  • Loaded DLLs
powershell.exe -enc <Base64 Payload>

1.3 DLL List

Each process maintains a linked list of loaded DLLs. Useful for detecting:

  • DLL Injection
  • Unusual DLL loading
  • Malicious modules

1.4 VAD Tree (Virtual Address Descriptor)

Tracks every memory region allocated to a process. Used to identify:

  • Memory allocations
  • Executable pages
  • Injected code
  • Memory permissions

The VAD Tree is one of the most important structures for detecting code injection. Since it is stored in kernel memory, it is much harder for malware to manipulate than user-mode structures like the PEB.

02Detecting DLL injection using the Windows API

Simple DLL Injection usually relies on a well-known sequence of Windows APIs:

OpenProcess()
VirtualAllocEx()
WriteProcessMemory()
CreateRemoteThread()
LoadLibraryA()

Since LoadLibrary() is used, Windows registers the DLL normally, making it visible in several process structures.

2.1 Where are loaded DLLs stored?

Process Environment Block (PEB) — contains linked lists of loaded modules:

  • InLoadOrderModuleList
  • InMemoryOrderModuleList
  • InInitializationOrderModuleList (InInit)

These are used by the dlllist and ldrmodules plugins.

Virtual Address Descriptor (VAD) — tracks every memory region of a process. Stores:

  • Base Address
  • Memory Protection
  • Mapped File Path

2.2 Volatility plugins: dlllist vs ldrmodules

dlllist — reads only the PEB. Shows loaded DLLs, base address, and load order. Cannot detect inconsistencies between the PEB and actual memory.

ldrmodules — reads information from both the PEB and the VAD. Much better for detecting hidden or suspicious DLLs. It compares:

ColumnMeaning
InLoadPresent in PEB Load List
InInitPresent in Initialization List
InMemPresent in Memory List
MappedPathOriginal file path from VAD
BaseDLL Base Address

2.3 What should analysts look for?

Suspicious DLL location — legitimate DLLs are normally loaded from C:\Windows\System32, C:\Windows\WinSxS, C:\Program Files. A suspicious example: C:\Temp\winsrv.dll. Indicators: loaded from a Temp folder, unusual filename, not part of the default Windows installation.

Why does svchost.exe show InInit = False? This is normal — the process executable itself is not included in the InInitializationOrderModuleList. Every normal process usually has one entry where InInit = False. Do not treat this alone as malware.

2.4 Memory forensics tools

  • Volatility — key plugins: dlllist, ldrmodules
  • MemProcFS — the findevil module can compare PEB and VAD and highlight anomalies automatically

03windows.ldrmodules — deep dive

3.1 Purpose

Examines DLLs loaded into a process. Instead of relying only on the PEB, it compares multiple loader structures to identify inconsistencies.

3.2 What it detects

  • Unlinked DLLs
  • Reflective DLL Injection
  • Non-memory-mapped modules

3.3 Why it matters

Malware may load a DLL and then remove it from the PEB:

DLL loaded into memory
  ↓
Removed from PEB
  ↓
windows.dlllist misses it
  ↓
windows.ldrmodules detects it

3.4 Purpose (comparison-based)

Unlike dlllist, ldrmodules does not rely only on the PEB — it compares information from the PEB and the VAD.

3.5 Information displayed

ColumnMeaning
PIDProcess ID
ProcessProcess Name
BaseBase address from VAD
InLoadPresent in InLoadOrder list
InInitPresent in InInitializationOrder list
InMemPresent in InMemoryOrder list
MappedPathFile path from VAD

3.6 Expected output

A legitimate DLL should have InLoad = True, InInit = True, InMem = True, and a MappedPath present. This indicates it was loaded through the Windows Loader, registered in the PEB, and mapped from disk.

3.7 Common false positives

  1. Process Executable — every process executable normally has InInit = False because executables are not stored in the Initialization list. Example: lsass.exe with InLoad=True, InInit=False, InMem=True is expected.
  2. Non-DLL image files — files such as .fon, .mui, .winmd, .msstyles may appear in Image Memory but are not DLLs, so they are absent from the PEB lists.
  3. Legitimate unloaded DLLs — sometimes a DLL remains mapped in the VAD but has not been loaded (or has already been unloaded); it may exist only in MappedPath without appearing in the PEB.
  4. SysWOW64 DLLs — Volatility 3 may incorrectly report some 32-bit SysWOW64 DLLs as missing from the PEB. It's recommended to compare results with Volatility 2.

3.8 Missing MappedPath — the strongest indicator

This is one of the strongest indicators of malicious activity. Normally, every legitimate DLL loaded via the Windows Loader has a file path. If no path exists, the DLL may have been reflectively injected, manually mapped, or may never have existed on disk at all.

3.9 How ldrmodules works

Instead of asking "What DLLs does the PEB report?", it asks "What executable memory exists according to the VAD?" — then compares the VAD against the PEB. Any mismatch becomes suspicious.

04Case studies

4.1 Example 1 — normal process

wininit.exe → ntmarta.dll:

  • InLoad = True
  • InInit = True
  • InMem = True
  • MappedPath present

Everything matches — this is normal.

4.2 Example 2 — Stuxnet

Process: lsass.exe. Two suspicious regions appear.

Region 1 — Base 0x80000. Missing from all PEB lists, no MappedPath → very strong evidence of an injected DLL.

Region 2 — Base 0x1000000. Present in PEB, InInit = False, no MappedPath. At first glance InInit = False looks normal (process executable), but MappedPath = empty is not normal — the executable should point to \Windows\System32\lsass.exe. Since no backing file exists, this indicates Process Hollowing: the original executable has been removed from memory and replaced with malicious code.

Correlating ldrmodules with malfind

Both tools can identify the same suspicious memory region (e.g. base 0x80000). If ldrmodules reports missing PEB/VAD consistency and malfind reports executable private memory, confidence in the detection increases significantly.

HollowFind

HollowFind (a Volatility 2 plugin) automates detection of Process Hollowing by comparing PEB, VAD, and process image information. It is built on the same consistency-checking concept used by ldrmodules.

05Reflective code injection

5.1 Definition

Reflective DLL Injection loads code without using LoadLibrary(). Instead, the malware contains its own loader called a Reflective Loader.

5.2 Why is it stealthier?

Normal DLL Injection:

LoadLibrary()
  ↓
Windows Loader
  ↓
DLL registered in PEB
  ↓
Easy to enumerate

Reflective Injection:

Reflective Loader
  ↓
DLL loaded manually
  ↓
No Windows Loader
  ↓
No PEB registration

Result: many security tools cannot see the injected DLL.

5.3 Advantages for attackers

  • No call to LoadLibrary()
  • No disk access required
  • Memory-only execution
  • Smaller forensic footprint
  • Harder to detect

5.4 Memory-only payloads

The payload can come directly from the network, shellcode, PowerShell, or a downloaded buffer — no DLL needs to exist on disk.

5.5 Common offensive frameworks

Many well-known tools use Reflective Injection: Metasploit, Cobalt Strike, PowerSploit, Empire, DoublePulsar. Nation-state malware has also adopted this technique.

5.6 Why is memory analysis important?

Reflective Injection hides from Process Explorer, DLL enumeration, and API monitoring. However, memory artifacts still remain — memory forensics is one of the best ways to detect it.

06The VAD tree in depth

Windows must record that a region of memory has been reserved. But where? Every reserved region gets its own structure: the Virtual Address Descriptor (VAD).

For example:

Start Address = 0x50000000
End Address   = 0x5000FFFF
Protection    = PAGE_READWRITE
Type          = MEM_PRIVATE

This single VAD describes the entire region. If a DLL is loaded — for example:

LoadLibrary("kernel32.dll")

— Windows creates a VAD for it as well. Every page has its own PTE (Page Table Entry), but a single VAD can span hundreds or thousands of pages, each with its own independent PTE.

07Investigation workflow

Run ldrmodules
        ↓
Compare PEB ↔ VAD
        ↓
Missing DLL?
        ↓
Missing MappedPath?
        ↓
PEB Lists Inconsistent?
        ↓
Likely Code Injection /
Reflective Injection /
Process Hollowing

08Key takeaway

dlllist trusts the PEB completely, which makes it fast but blind to anything the malware has hidden from the loader's own bookkeeping. ldrmodules closes that gap by cross-referencing the PEB against the VAD — the same "trust but verify across independent sources" principle we saw with pslist vs psscan in Part 01. A missing MappedPath, an unexpected InInit = False on a non-executable module, or a region flagged by both ldrmodules and malfind are the strongest signals of DLL injection, reflective injection, or process hollowing.
