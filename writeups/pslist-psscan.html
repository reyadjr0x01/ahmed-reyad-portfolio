WINDOWS MEMORY FORENSICS · PART 01

pslist & psscan: two different views of the same memory image

Volatility can tell you what processes were running on a system in more than one way — and the two most basic plugins don't always agree. Understanding why is the first real lesson in Windows memory forensics.

Series · Windows Memory Forensics Stack · Volatility 3 · _EPROCESS · DKOM Read · ~14 min

When analyzing a Windows memory image with Volatility, one of the first questions we usually ask is: what processes were present on the system? At first that sounds simple — run pslist, get a list, start investigating. But memory forensics gets interesting once we ask a harder question: how does Volatility actually know that a process exists?

To answer that, we need to understand how Windows represents processes in kernel memory. This part covers how Windows represents processes using _EPROCESS, the role of ActiveProcessLinks, how pslist enumerates processes and why it can miss some, how psscan discovers process objects directly from memory using pool tags, why psscan can return terminated or stale objects, and why comparing the two plugins is a core forensic workflow.

01Volatility 2 vs Volatility 3

The commands differ between framework versions, though the underlying Windows concepts don't change.

Volatility 2

vol.py -f memory.raw pslist
vol.py -f memory.raw psscan

Volatility 2 used Windows profiles and older symbol mechanisms to understand kernel structures.

Volatility 3

python vol.py -f memory.raw windows.pslist
python vol.py -f memory.raw windows.psscan

Volatility 3 uses a newer, symbol-based architecture. The framework changed — the concepts we're investigating (_EPROCESS, process lists, process objects in memory) did not.

02pslist — enumerating the active process list

The easiest way to think about pslist: it follows Windows' active process list and enumerates whatever is connected to it.

_EPROCESS — the Windows process object

Windows represents each process with an internal kernel structure called _EPROCESS, containing fields such as UniqueProcessId, InheritedFromUniqueProcessId, ImageFileName, ActiveProcessLinks, Peb, and ObjectTable. The exact layout isn't fixed across Windows versions and builds — fields move and get reinterpreted. What matters for forensics is the concept: an _EPROCESS object represents a process inside kernel memory. One field is central to pslist: ActiveProcessLinks.

What is ActiveProcessLinks?

ActiveProcessLinks is a linked-list entry embedded inside _EPROCESS, using the Windows LIST_ENTRY concept (a Flink/Blink pair). Windows maintains a doubly linked list of active processes, with a head commonly associated with PsActiveProcessHead:

PsActiveProcessHead
        |
        v
   _EPROCESS <-> _EPROCESS <-> _EPROCESS <-> ...
Important distinction: PsActiveProcessHead is the list head, not an _EPROCESS object itself. Volatility uses the ActiveProcessLinks offset to recover the surrounding _EPROCESS object and pull process information from it.

How pslist actually works

Memory Image -> Kernel Structures -> PsActiveProcessHead
    -> ActiveProcessLinks -> _EPROCESS (PID, PPID, ImageFileName, CreateTime)
    -> next ActiveProcessLinks -> next _EPROCESS -> ...

So windows.pslist isn't searching memory for process names — it's walking Windows' own understanding of "which processes are active," using kernel structure knowledge. Instead of "pslist gives me processes," think: pslist gives me the processes reachable through the active process list. That distinction matters a great deal during rootkit investigations.

03The blind spot of pslist

What happens if a malicious kernel-level component modifies the process list directly? One technique for this is DKOM — Direct Kernel Object Manipulation, where an attacker manipulates kernel objects directly.

Normal:
PsActiveProcessHead -> explorer.exe -> svchost.exe -> malware.exe

After DKOM:
PsActiveProcessHead -> explorer.exe -> svchost.exe

malware.exe's _EPROCESS still exists in memory,
but is no longer linked into the active process list.

The process object can still exist in memory even though it's no longer reachable through the list. Since pslist depends on that list, it may simply not see it. Not appearing in pslist does not prove a process never existed.

04psscan — searching memory for process objects

This is where psscan takes a different approach: instead of following ActiveProcessLinks, it searches memory for structures that look like process objects — which means understanding the Windows kernel pool.

Windows dynamically allocates kernel objects from memory pools, and each pool allocation can carry identifying metadata known as a Pool Tag. For a process object, the pool tag associated with _EPROCESS is Proc. Conceptually:

Search memory for pool allocations
    -> look for "Proc" tag indicators
    -> check the surrounding structure
    -> does the data make sense?
         yes -> potential _EPROCESS
         no  -> ignore / invalid candidate

It's not simply "find the word Proc and call it a process" — the scanner combines the tag with the surrounding memory structure and expected process-object characteristics. This is why psscan can potentially find a process even when it's no longer connected to the active process list.

05Why can psscan find more processes?

Suppose pslist returns System, explorer.exe, svchost.exe — but psscan also returns a fourth entry, suspicious.exe. At first glance that looks like hidden malware. It isn't automatically that. Three explanations are common:

  • Active but unlinked — the _EPROCESS object may still exist in memory while no longer reachable through ActiveProcessLinks, consistent with DKOM-style hiding.
  • Recently terminated — a process can terminate while parts of its kernel object remain in memory; psscan can recover remnants of processes no longer active at acquisition time.
  • Stale or reused memory — kernel memory is constantly allocated and freed, and a region that once held a process object can still contain enough recognizable data to be identified. A psscan hit does not automatically mean "this was running at acquisition time."

Neither plugin is "better" — they provide different views of the same memory image. pslist asks what's reachable through the active list; psscan asks what process objects can be discovered independently of it.

07The most important forensic scenario

The interesting case is a process — say malware.exe, PID 1800 — that appears in psscan but not in pslist. That's a forensic discrepancy, and a lead, not a verdict. Possible explanations: recently terminated, unlinked/hidden, a stale process object, or a memory/acquisition artifact. We still have to investigate it.

08Investigating the discrepancy

Once a process shows up only in psscan, correlate it with additional evidence:

  • Process lifetime — check CreateTime / ExitTime to see whether the object represents an already-terminated process. No single field is absolute proof either way.
  • Parent process — check InheritedFromUniqueProcessId. Does the parent-child relationship make sense (explorer.exe → suspicious.exe vs. services.exe → legitimate_service.exe)?
  • Threads — do the process's threads look consistent with an active process, or with a leftover object?
  • Virtual memory — investigate the address space (covered in the next part on VAD analysis).
  • Loaded modules — expected modules vs. suspicious DLLs, unusual regions, injected or manually mapped code.
  • Handles — interactions with files, registry keys, other processes, threads, and Windows objects.
  • Network activity — connections, remote IPs, listening ports, sockets.

The goal throughout: figure out what this process was actually doing.

09Why use both together

Running only pslist means relying entirely on the active process list. Running only psscan means you may encounter terminated or stale remnants with no easy way to tell them apart. Comparing both — pslist + psscan → discrepancy → further investigation — produces a far stronger workflow than either alone. The goal isn't a plugin that says "this is malware." It's identifying inconsistencies worth investigating with additional evidence.

10Practical workflow

  1. Run pslist — python vol.py -f memory.raw windows.pslist. Note PID, PPID, process name, creation time, and relationships.
  2. Run psscan — python vol.py -f memory.raw windows.psscan. Compare against pslist, and flag psscan-only processes.
  3. Investigate the discrepancy — for every interesting PID: was it active? terminated? does the parent make sense? suspicious memory, modules, or network activity?
  4. Go deeper — VADs, memory mappings, injected code, loaded modules, handles, network artifacts, command line. This is where process enumeration turns into real memory forensics.

11Key takeaway

pslist ≠ psscan. They aren't two commands that happen to produce the same list — they use fundamentally different approaches to identify processes. pslist tells you what's exposed through the active process list; psscan tells you what process objects can be discovered independently of it. When the results disagree, don't immediately label the process malicious — investigate why the views disagree: terminated process, stale memory, an unlinked/hidden process, or a memory/acquisition artifact. That mindset matters more than memorizing plugin syntax.

Windows memory forensics is fundamentally about understanding how the OS represents state in memory. For process analysis, that starts with _EPROCESS and its ActiveProcessLinks, and from there, why pslist and psscan can disagree — and why that disagreement is where the real forensic value lives.
